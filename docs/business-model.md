# Business model, provider prices, and unit economics

This is the operator's working document for the gateway's money. It answers four
questions: what each upstream charges us, what we sell it for, what the free
allowance costs, and how much paid revenue has to exist before the free tier
pays for itself.

Every number below the first marker is generated by
`npm run business-model`, which reads `data/gateway.db` and the dated provider
snapshot in [`docs/data/provider-prices.json`](data/provider-prices.json). Edit
prose freely; edit numbers only in code, so the document cannot drift from the
database.

## What we sell

Three billing groups, one catalog:

| Group          | Who pays            | How it settles                                                              |
| -------------- | ------------------- | --------------------------------------------------------------------------- |
| `free`         | Nobody              | Shared daily weighted-token allowance, split across activated accounts      |
| `paid`         | The customer        | Prepaid credit, reserved on admission and settled on the final token report |
| `subscription` | The customer's plan | Included allowance inside a billing period, then overage at the paid rate   |

Two funding paths feed `paid`: Stripe top-ups (credit that never expires) and
operator credit grants. The subscription tables and Stripe lifecycle code exist
and are tested, but no plan is on sale, so plan revenue is currently zero by
decision rather than by accident. See
[`docs/subscriptions-decision.md`](subscriptions-decision.md).

## The three upstreams

We buy tokens from independent resellers and sell one catalog in front of them.
Provider identity is recorded per request (`usage_events.provider_slug`), so
margin can be attributed by upstream rather than guessed at.

- **Apinex** — the default upstream (`savant` slug), fully synced. This is where
  the current 44-model catalog and all of its cost data comes from.
- **CommandCode** — registered and enabled, OpenAI and Anthropic wire formats,
  no catalog synced yet because `COMMANDCODE_API_KEY` is unset.
- **Apixo** — registered at install with base URL `https://api.apixoai.online/v1`,
  dual wire format, key variable `APIXO_API_KEY`. It ships **disabled**: its
  catalog endpoint needs a key, so enabling it before the key exists would fail
  every sync. Published rates are recorded in
  [`docs/data/provider-prices.json`](data/provider-prices.json) with the capture
  date. It documents no balance or subscription endpoint, so those capabilities
  stay off and credit has to be checked in its dashboard.

The point of three upstreams is not redundancy for its own sake. It is that the
same model is often cheaper at one of them, so the sell price can stay fixed
while the cost side moves.

## How the free allowance behaves

The upstream plan grants one weighted-token pool per UTC day for the whole
account. We do not hand every customer that pool. We allocate a configured
share, split evenly across activated accounts (an active customer holding at
least one active key), and hold the rest as a reserve:

- 20,000,000 weighted tokens/day → 90% allocatable = 18,000,000/day, 2,000,000 reserve.
- 5 activated accounts → 3,600,000 each.
- A 6th account joining mid-day rebalances the unspent remainder to 3,000,000 each.
- Usage already recorded is never clawed back; a newcomer only receives capacity
  nobody spent.

Because the allowance is free at the upstream, the free tier costs nothing while
it lasts. The exposure is what happens at exhaustion: either the request is
refused, or it is served from a funded wallet at the costs in the generated
section. That choice is the single biggest lever on early losses, and it is why
the numbers below matter before any traffic exists.

## The margin rule

Cost is synced from the provider; the sell rate is cost × (1 + markup), with the
markup held in `pricing.markup_bps`. At the default 30%, gross margin is
`0.30 / 1.30 = 23.1%` of revenue. That is the budget out of which the free tier,
failed requests, refunds, and payment fees all have to be paid. A deeper public
discount than the markup allows is a loss on every paid request, not a
marketing cost that averages out.

## Adding an upstream

1. Read its docs and record the published rates in `docs/data/provider-prices.json`
   with the capture date. Published pages are the only source allowed here.
2. Add the provider in Admin → Providers: slug, label, wire format, base URL,
   and the environment variable that will hold the key. Keep it disabled until
   the key exists.
3. Put the key in `.env.local` only, restart, then sync. A sync imports only
   that provider's rows and namespaces their public ids (`apixo/<model>`), so it
   cannot touch the default catalog.
4. Compare the synced cost with the incumbent before routing traffic: the pivot
   table in the generated section shows where the new upstream is cheaper.
5. Leave the row disabled if the catalog arrives without prices. A model with
   no synced cost would sell at zero, which is worse than not selling it.

## What to watch

- **Price-feed plausibility.** The current feed prices 40 of 45 rows with
  identical input and output rates and only 15 distinct price points. Real
  catalogs price completion tokens higher. Until that is confirmed against the
  reseller's own rate card, savings figures on `/models` are arithmetic, not
  evidence.
- **Allowance abuse.** One person creating several accounts multiplies their
  share. Activation requires an active key, so key creation is the throttle that
  matters.
- **Reserve discipline.** The 10% reserve exists for bursts and provider
  disagreement about weighted tokens. Allocating it away turns every estimate
  error into a hard stop.
- **Provider concentration.** One upstream holds the free pool and the whole
  catalog. A second synced provider is the only real hedge.
- **Cache.** Re-sent prompts are the dominant token cost in agent traffic. If the
  upstream bills cached tokens separately, our sell price has to follow or the
  discount is paid for twice.
