# FID-2026-1030-060 — measured load and resilience closure (2026-10-31)

Request: implement FID-2026-1030-060 load and resilience acceptance with real
measurements. Automation level 3, strict, single agent. No deployment, real
provider call, spend, operator approval or hosted receipt was created.

## Implementation

- **Envelope:** `config/load-envelope.json` carries serving RPM/concurrency,
  fixture delay, body/stream bounds, 387 offered calls, latency/error targets,
  512 MB RSS and 256 MB database budgets, reconciliation limits and 30%
  headroom. Its status is `candidate`; no operator approval exists.
- **Runner:** `scripts/load-acceptance.mjs` boots the production artifact and a
  disposable SQLite file, seeds a fixture provider/catalog/accounts, and runs
  `scripts/load/*` for ramp, steady, burst, mixed billing, long streams,
  cancellation, key churn, competing reservations, provider 429/5xx/disconnect/
  malformed/truncated responses, quota reset, database contention, alert
  failure, drain, process crash and a storage-write rejection.
- **Independent accounting:** dispatch is counted at the fixture upstream;
  settlements, usage, ledger and held/quarantined credit are read from SQLite.
  The verdict fails on any unresolved admission, committed/usage mismatch,
  ledger or hold difference, unexpected status, missing resource measurement or
  target miss.
- **Repair:** a clean SSE close without `[DONE]` was settled as `ok`; it now
  settles as `error`, releases admission and never forwards `[DONE]`. Four HTTP
  checks cover the regression.
- **Tests:** `tests/capacity-invariants.test.mjs` (5) covers interleaved
  admission, refusal without RPM spend, alias sharing, idempotent release and
  unknown ceilings.
